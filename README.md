# Local AI Scheduler

Локальный ИИ-ассистент для управления расписанием через естественный язык.

Проект предназначен для создания сервиса, который принимает сообщения пользователя в свободной форме — текстом или голосом — понимает намерение пользователя, извлекает задачи и временные ограничения, формирует структурированное расписание и в дальнейшем передаёт его в сервис календаря.

Основная идея — отделить интерфейс пользователя, обработку естественного языка, планирование и работу с календарём друг от друга. Благодаря этому один и тот же AI-сервис сможет использоваться через desktop-приложение, Telegram-бота, веб-интерфейс и другие клиенты.

---

## 1. Цель проекта

Пользователь должен иметь возможность сказать или написать что-то вроде:

> «Завтра утром позаниматься английским, потом подготовить отчёт, в три созвон с начальником, а после работы зайти в магазин. Вечером хочу посмотреть фильм».

Система должна:

1. принять текст;
2. при необходимости обработать голосовое сообщение через Speech-to-Text;
3. определить, является ли сообщение новым запросом или продолжением предыдущего;
4. понять намерение пользователя;
5. извлечь задачи;
6. определить даты, время, длительность и ограничения;
7. учитывать предыдущие сообщения пользователя;
8. преобразовать естественный язык в структурированную команду;
9. построить реалистичное расписание;
10. проверить полученный результат;
11. передать готовые события отдельному сервису календаря.

Главный принцип:

**LLM отвечает за понимание естественного языка, а детерминированная логика Python — за даты, время, расчёты, проверки и бизнес-правила.**

# 2. Основные требования

## К модели

Используется локальная модель:

- Qwen3 8B;
- запуск через Ollama;
- работа без внешнего облачного API;
- хорошее понимание русского языка;
- поддержка Structured Outputs / JSON Schema;
- приемлемая работа на обычном ПК.

Текущая модель:

```text

```

Модель должна рассматриваться как заменяемый компонент. Архитектура не должна зависеть от конкретной LLM.

В будущем модель можно заменить без изменения API сервиса.

# 6. Ollama Client

Для работы с локальной моделью используется отдельный класс:

```python
class OllamaClient:
    ...
```

Его задача — только взаимодействие с Ollama.

Он должен получать настройки из `.env`:

```text
OLLAMA_URL
OLLAMA_MODEL
OLLAMA_TIMEOUT
OLLAMA_API_KEY
```

Класс не должен знать:

```text
├── check_connection()
└── reset_model()
```

Это позволит в будущем заменить Ollama или модель без изменения остального приложения.

# 7. Structured Output

LLM не должна возвращать произвольный текст.

Для ответов используются структурированные данные по JSON Schema.

Пример:

```json
{
  "date": "2026-08-27",
  "events": [
    {
      "title": "Созвон с начальником",
      "start": "15:00",
      "duration_minutes": 45,
      "tag": "работа",
      "description": "Созвон с начальником"
    }
  ]
}
```

Однако JSON Schema является только первым уровнем проверки.

Общий процесс:

```text
LLM
 ↓
JSON Schema
 ↓
Pydantic
 ↓
Business Validation
 ↓
Final Schedule
```

# 8. LLM не должна самостоятельно вычислять всё расписание

Важный принцип проекта:

**LLM интерпретирует естественный язык, Python выполняет детерминированные операции.**

Например пользователь говорит:

> «Напомни через час».

LLM должна определить:

```json
{
  "type": "relative_time",
  "amount": 1,
  "unit": "hour"
}
```

Python уже вычисляет конкретное время:

```text
текущее время + 1 час
```

Аналогично:

> «завтра»

LLM определяет:

```text
relative_date = tomorrow
```

Python вычисляет:

```text
текущая дата + 1 день
```

Это уменьшает количество ошибок и галлюцинаций.

# 9. Обработка времени

Временные выражения условно делятся на несколько категорий.

## Простые выражения

Могут обрабатываться детерминированно:

```text
сегодня
завтра
послезавтра
через 30 минут
через час
через 2 часа
в 15:00
в 18:30
утром
днём
вечером
ночью
```

Для таких выражений можно использовать Python и регулярные выражения.

---

## Неоднозначные выражения

Например:

```text
часика через полтора
ближе к вечеру
после работы
часов в пять
с утра, но не слишком рано
как освобожусь
после обеда
```

Такие конструкции лучше отдавать LLM для семантического анализа.

LLM должна вернуть нормализованное представление, а не обязательно окончательное время.

Например:

```json
{
  "time_expression": {
    "type": "semantic",
    "value": "after_work"
  }
}
```

После этого Python Scheduler определяет конкретное время на основе доступного контекста.

# 10. Контекст сообщений

Пользователь может разделить один запрос на несколько сообщений.

Например:

```text
Сообщение 1:
"Завтра поставь тренировку"

Сообщение 2:
"Часа на полтора"
```

Второе сообщение является продолжением первого.

Поэтому система должна временно хранить контекст пользователя.

На первом этапе можно использовать обычную память процесса:

```text
user_id
 ├── recent_messages
 ├── pending_command
 └── last_activity
```

В будущем при масштабировании контекст можно перенести в Redis или другую внешнюю систему хранения.

# 11. TTL и окно объединения сообщений

Нужно различать два параметра.

## Message Merge Window

Например:

```text
MESSAGE_MERGE_WINDOW_MINUTES=5
```

Если новое сообщение пришло в течение этого времени, оно рассматривается как потенциальное продолжение предыдущего.

Но это только один из признаков.

---

## Context TTL

Например:

```text
CONTEXT_TTL_MINUTES=60
```

Сообщения могут храниться в контексте до часа.

После истечения TTL старый контекст удаляется.

---

# 12. Определение продолжения сообщения

Нельзя использовать только временной интервал.

Например:

```text
"Завтра тренировка"

через 2 минуты:

"Часа на полтора"
```

Очевидно похоже на продолжение.

Но:

```text
"Завтра тренировка"

через 2 минуты:

"А ещё купи молоко"
```

это уже новое событие.

Поэтому используется гибридный подход:

```text
Временной интервал
        +
Текст нового сообщения
        +
Предыдущий контекст
        +
LLM classifier при необходимости
```

Сначала можно применять простые правила.

Если ситуация неоднозначная — использовать отдельный короткий LLM-запрос:

```text
Является ли новое сообщение продолжением предыдущей команды?
```

LLM должна вернуть структурированный результат:

```json
{
  "continuation": true
}
```

или:

```json
{
  "continuation": false
}
```

# 13. Pending Command

Особенно полезно хранить не только историю сообщений, но и незавершённую команду.

Например:

```text
Пользователь:
"Завтра хочу сходить в спортзал"
```

Система понимает:

```text
intent = create_event

title = Спортзал
date = tomorrow

missing:
- duration
- exact time
```

Команда может получить статус:

```text
waiting_for_clarification
```

Следующее сообщение:

```text
"Часа на полтора"
```

объединяется с ожидающей командой.

Получается:

```text
Спортзал
Дата: завтра
Продолжительность: 90 минут
```

```json
      "date": "tomorrow",
```

После этого Python Scheduler:

# 15. Проверка расписания

Даже если JSON полностью соответствует схеме, он может быть логически неправильным.

Например:

```text
14:00–16:00 Подготовка отчёта
15:00–15:45 Созвон
```

JSON валидный.

Расписание — нет.

Поэтому необходима отдельная проверка.

Проверяется:

- корректность даты;
- корректность времени;
- корректность длительности;
- отсутствие пересечений;
- наличие обязательных событий;
- отсутствие дубликатов;
- допустимые теги;
- логические ограничения;
- реалистичность расписания.

# 17. API

Первоначальный API:

```text
GET /health
```

Проверка работоспособности сервиса и соединения с Ollama.

---

```text
POST /message
```

Основной endpoint.

Пример запроса:

```json
{
  "user_id": "desktop",
  "text": "Завтра в три часа созвон с начальником на 45 минут"
}
```

---

```text
POST /reset/context
```

Удаление контекста пользователя.

Используется, если модель начинает учитывать ненужную предыдущую информацию.

---

```text
POST /reset/model
```

Сброс/выгрузка модели из памяти Ollama.

Это не означает очистку истории сообщений.

Это две разные операции:

```text
/reset/context → очистить контекст
/reset/model   → выгрузить модель
```

# 22. Почему используется гибридный подход

Главная архитектурная идея проекта:

```text
LLM = понимание языка
Python = детерминированная логика
```

LLM хорошо подходит для:

- понимания русского языка;
- определения намерения;
- извлечения задач;
- понимания неформальных формулировок;
- определения контекста;
- определения продолжения сообщения;
- интерпретации неоднозначных временных выражений.

Python лучше подходит для:

- вычисления дат;
- вычисления относительного времени;
- проверки пересечений;
- проверки длительности;
- TTL;
- хранения контекста;
- бизнес-правил;
- валидации;
- работы с API;
- обработки ошибок.

Это позволяет уменьшить влияние галлюцинаций модели.

# 25. Приоритеты разработки

Разработка должна идти постепенно.

## Этап 1 — AI Scheduler

Сделать:

```text
FastAPI
    ↓
Ollama
    ↓
```

# 26. Главный принцип проекта

Проект не должен превращаться в систему, где LLM самостоятельно принимает все решения.

Правильная модель:

```text
                Natural Language
                       │
                       ▼
                      LLM
                       │
                       │ понимание
                       ▼
              Structured Command
                       │
                       ▼
              Deterministic Python
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
        Dates        Time        Validation
          │            │            │
          └────────────┼────────────┘
                       ▼
                  Final Schedule
                       │
                       ▼
                 Calendar API
```

**LLM является интеллектуальным интерпретатором, а не единственным источником истины.**

Это основной архитектурный принцип, на котором должен строиться дальнейший проект.

# Будущая установка из репозитория

---

Проект должен предусматривать возможность установки всей системы непосредственно из репозитория.

В будущем предполагается автоматизированный установщик для Windows, например:

```text
install.bat
```

Установщик должен:

1. проверить наличие необходимых компонентов;
2. установить Python-зависимости;
3. создать виртуальное окружение;
4. проверить наличие Ollama;
5. установить/загрузить необходимую локальную LLM;
6. создать `.env` на основе шаблона;
7. записать минимально необходимые настройки;
8. создать необходимые директории;
9. проверить работоспособность сервисов;
10. вывести пользователю дальнейшие инструкции.

Конфиденциальные данные не должны храниться в репозитории.

В репозитории должен находиться:

```text
.env.example
```

а реальный:

```text
.env
```

должен создаваться установщиком и находиться в `.gitignore`.

После завершения установки пользователь должен получить понятную инструкцию о необходимых ручных действиях: настройке API-токенов, авторизации в Яндекс Календаре, настройке Telegram-бота и других внешних сервисов.

В дальнейшем установщик может быть расширен до полноценного bootstrap-механизма всей системы.
